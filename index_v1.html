개요

카메라 없이 Wi-Fi 신호의 미세한 변화(CSI)를 분석해 실내 낙상을 감지하는 시스템입니다. 사생활 침해 없이 고령자의 낙상을 감지하는 것을 목표로, ESP32로 수집한 신호를 딥러닝 모델로 판별하고 결과를 Android 앱으로 전달해 보호자가 즉시 확인할 수 있도록 구현했습니다.

기간 · 인원

  • 2026.03 ~ 2026.08
  • 이다연 (APP·EM) · 염세현 (BE·EM) · 이지우 (AI)

주요 기능

  • 카메라 없이 Wi-Fi CSI로 실내 낙상을 실시간 감지
  • 낙상 감지 시 보호자 앱으로 즉시 알림 전송
  • 기기 등록·선택 및 상태 확인
  • ESP32 → 서버 → 앱으로 이어지는 실시간 데이터 연동

맡은 역할

ESP32 STA 펌웨어 개발
  • Wi-Fi STA 모드로 공유기에 접속해 ESP32에서 CSI(Channel State Information) 신호를 실시간 수집
  • 수집한 CSI 원신호(64개 서브캐리어)를 서버로 전송하는 통신 로직 구현
  • 연결 유지·재연결 처리로 신호가 끊기지 않도록 전송 흐름을 안정화
  • 헤더(.h)/소스(.c) 분리, @brief·@param 등 Doxygen 스타일 주석으로 함수 문서화
  • 함수·변수 역할과 코드 구조를 정리하며 펌웨어 기본기 확립
Android 앱 개발
  • 실시간 낙상 감지 결과 표시 및 보호자 알림 화면 구현
  • 기기 등록·선택·상태 확인 화면 구현
  • 서버(MQTT)로 수신한 위험 상태를 앱 UI에 실시간 반영

주요 성과

  • 약 50개 팀 참가 → 예선 30 → 15팀 통과, 본선 진출
  • 최종 장려상 수상 (은상과 1팀 차)
  • 펌웨어–서버–앱 전체 연동을 완성해 실시연까지 진행

문제 해결

앱–펌웨어 연동이 반복적으로 끊기는 문제

문제 배경

개발 중 휴대폰 핫스팟 환경에서 앱과 펌웨어를 연동해 테스트했는데, 통신이 주기적으로 끊겨 데이터 수신이 불안정했습니다.

해결 방법

원인이 핫스팟이 UDP 트래픽을 주기적으로 차단하는 데 있음을 확인하고, 별도 공유기 환경으로 전환해 안정적인 통신을 확보했습니다.

통신 기능을 STA 모드에 둘지 AP 모드에 둘지

문제 배경

앱 연결과 서버 전송 기능을 ESP32의 STA(기존 Wi-Fi 접속) 모드에서 처리할지, AP(기기가 직접 네트워크를 제공) 모드에서 처리할지 결정해야 했습니다. 두 방식은 연결 안정성, 초기 설정 편의성, 서버 접근성에서 장단점이 달랐습니다.

해결 방법

서버로의 데이터 전송과 안정적인 연결이 핵심 요구사항이라고 판단해, 기존 네트워크에 접속하는 STA 모드를 기준으로 통신 구조를 구성했습니다. 기술을 먼저 정하기보다 요구사항을 먼저 정의하고 모드를 선택하는 과정이었습니다.

회고

가장 걱정했던 펌웨어–서버–앱 전체 연동이 예상보다 잘 풀려 실제 서비스처럼 동작하는 것을 확인했을 때 큰 성취감을 느꼈습니다. 펌웨어를 직접 구조부터 작성하며 처음으로 코드를 짜는 재미와 자신감을 얻었고, 통신 구조를 어디에 둘지 고민하며 '기술을 먼저 정하기보다 요구사항을 먼저 정의해야 한다'는 것을 배웠습니다. 예선에서는 확장성 관련 Q&A에 잘 답하지 못했지만 본선에서는 발표 연습을 거듭해 안정적으로 마쳤고, 현업 개발자·성인 참가자가 많은 대회에서 장려상을 받으며 결과보다 과정에서 더 많은 것을 얻은 프로젝트였습니다.

개요

WRO Future Engineering은 사전 정보가 주어지지 않은 트랙을 완전 자율로 주행하는 로봇 대회입니다. 차량은 카메라로 주변을 인식하며 세 바퀴를 주행하고, 무작위로 배치된 빨강·초록 표지판을 실시간으로 판단해 좌우로 회피하며, 마지막에는 지정 구역에 평행주차까지 수행해야 합니다. 저는 하드웨어 제작부터 주행 소프트웨어 튜닝까지 전 과정에 참여했습니다.

기간 · 인원

  • 2026.06 ~ 2026.09
  • 이다연 · 염세현

담당 역할

  • 라즈베리파이와 OpenCV 기반의 비전 라이브러리를 활용해, 카메라로 색상 블록을 인식하고 회피 방향을 결정하는 주행 로직을 구성하고 환경에 맞게 튜닝했습니다.
  • 초음파 센서 기반의 트리거 동작을 구현해 특정 조건에서 차량이 반응하도록 했습니다.
  • PID 제어와 4륜 구동 차량의 구조를 이해한 바탕 위에서 하드웨어 조립·제작에 참여했습니다.

문제 해결

  • 조명과 바닥 환경이 달라지면 동일한 색 블록이 카메라에 다른 값으로 인식되는 문제가 있었습니다. 노출·채도 등 파라미터를 환경마다 다시 맞추는 튜닝 절차를 정립하여, 어떤 환경에서도 빠르게 재보정할 수 있도록 대응했습니다.
  • 바닥 마찰이 큰 환경에서는 우회전(초록 표지판 회피)이 좌회전보다 둔하게 동작했습니다. 경기장 조건에 맞춰 모터 속도 값을 세밀하게 조정해 좌우 회피 동작의 균형을 맞췄습니다.

회고

소프트웨어뿐 아니라 하드웨어를 함께 다루면서, 비전 시스템이 환경 변화에 얼마나 민감한지, 그리고 그 변화를 '다시 맞출 수 있도록 절차화'하는 것이 실전에서 얼마나 중요한지를 배웠습니다.

개요

반지하·저지대 거주자는 집중호우 시 침수 위험에 취약하지만, 이를 미리 감지하고 대비할 수단이 부족합니다. 우물집(wellHouse)은 IoT 센서로 침수 위험을 감지해 사용자에게 알리고 대비를 돕는 서비스입니다. 3일간의 해커톤 동안 디자인·앱·백엔드·펌웨어·하드웨어가 하나의 서비스로 동작하도록 전체 흐름을 완성했습니다.

기간 · 인원

  • 2026 · 3일 해커톤
  • 이다연 (APP·BE) · 손서원 (EM) · 김수인 (DESIGN) · 하채은 (EM) · 김경태 · 권지성 · 김정현

담당 역할

  • Android 앱과 Spring Boot 백엔드를 단독으로 맡아 개발했습니다.
  • 센서 데이터가 백엔드 서버를 거쳐 앱 화면까지 전달되는 전체 데이터 흐름을 직접 설계하고 연결했습니다.
  • 수위·환경 데이터를 위험 등급으로 판정하는 로직과 단계를 직접 설계·구현했습니다.
  • 서보모터로 두꺼비집·창문을 제어하는 펌웨어와 하드웨어도 팀원과 함께 수정·보완하며 완성도를 높였습니다.

문제 해결

  • 펌웨어–앱 연동 시 수위 값이 계속 어긋나는 문제
    • 수위센서 ADC 값을 cm로 환산하는 지점이 펌웨어·앱 양쪽에 흩어져 있어 값이 불일치
    • 펌웨어에서 한 번만 계산해 앱으로 전달하도록 구조를 통일해 해결 (앱·펌웨어 모두 수정)
  • 센서 값을 앱에 실시간으로 반영해야 하는 문제
    • 펌웨어(ESP32) → 서버는 MQTT로 수신, 서버 → 앱은 WebSocket으로 실시간 push, 위험 경보는 FCM으로 전송하는 구조를 설계·구현
    • 센서 값이 올라오면 위험도 평가 후 즉시 앱 화면에 반영되도록 데이터 흐름을 연결

회고

  • 3일간 한 프로젝트에만 몰입하며, 앱 화면 구현을 넘어 센서 → 서버 → 앱 전체 흐름을 직접 연결
  • '혼자면 더 빠를까' 싶은 순간도 있었지만, 팀원 덕분에 놓친 문제를 발견하고 완성도를 높임
  • 협업은 단순한 역할 분담이 아니라 서로의 결과물을 더 나은 방향으로 끌어올리는 과정임을 배움
  • 짧은 몰입이 수상으로 이어져 팀과 함께 성취감을 나눈 인상 깊은 경험

개요

도로 파손·포트홀은 신고와 관리가 번거롭고 데이터로 축적하기 어렵습니다. Pixel은 사용자가 자연어로 요청하면 도로 이미지를 분석해 파손을 탐지하고, 관련 문서와 공공데이터를 검색해 리포트까지 자동으로 생성하는 멀티모달 AI 플랫폼입니다. 지엔소프트 기업 프로젝트로 진행했으며, 디자인을 제외한 프론트엔드·백엔드·AI·배포 전 영역을 직접 담당했습니다.

기간 · 인원

  • 2026.06 ~ 2026.07
  • 이다연 · 염세현 · 하채은 · 김근영

담당 역할

  • 커스텀 YOLO 모델로 도로 파손·포트홀을 탐지하고, VLM(Vision-Language Model)로 이미지 상황을 설명하는 기능을 구현했습니다.
  • BM25와 시맨틱 검색을 결합한 RAG로 문서 검색을 구성하고, 공공데이터(data.go.kr)를 연동했습니다.
  • 활동 로그와 검색 결과를 바탕으로 리포트를 자동 생성(PDF/DOCX)하는 기능을 개발했습니다.
  • React 프론트엔드와 FastAPI 백엔드를 구축하고, 라즈베리파이·Docker 환경에 배포했습니다.

기술 포인트

  • 작업 성격에 따라 로컬 LLM과 외부 API 경로를 분리 — 텍스트 작업은 빠른 외부 API로 직행하도록 배선을 바꿔 응답 시간을 약 50초 → 10초로 단축
  • 하이브리드 RAG(BM25 자체 구현 + 임베딩 + RRF 융합)를 구성하고, 검색 단계에서 근거 부족을 판별해 환각을 차단
  • 좌표 정확도가 낮은 VLM 대신 grounding을 네이티브로 학습한 모델로 교체해 라벨링 박스 정확도 개선
  • Gemini → 로컬 LLM → OpenAI 폴백 체인으로 장애 시에도 기능이 중단되지 않도록 안정성 확보

회고

이론으로만 알던 RAG·캐싱·인증을 실제 코드로 구현하며 몸으로 이해했고, '가장 유명한 도구'가 아니라 '제약과 목적에 맞는 도구'를 고르는 감을 잡았습니다. 프롬프트를 아무리 다듬어도 해결되지 않을 때는 모델의 동작 원리를 이해해야 교체를 결정할 수 있다는 것, 라즈베리파이라는 제약이 오히려 폴백·캐시 같은 더 단단한 구조를 만들게 한다는 것을 배웠습니다. 마지막으로 실시연을 직접 준비하며 '개발의 마지막은 코드 완성이 아니라 결과를 전달하는 것'임을 체감했습니다.
