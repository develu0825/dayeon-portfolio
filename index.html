개요

카메라 없이 Wi-Fi 신호의 미세한 변화(CSI)를 분석해 실내 낙상을 감지하는 시스템입니다. 사생활 침해 없이 고령자의 낙상을 감지하는 것을 목표로, ESP32로 수집한 신호를 딥러닝 모델로 판별하고 결과를 Android 앱으로 전달해 보호자가 즉시 확인할 수 있도록 구현했습니다.

주요 기능

  • 카메라 없이 Wi-Fi CSI로 실내 낙상을 실시간 감지
  • 낙상 감지 시 보호자 앱으로 즉시 알림 전송
  • ESP32 → 서버 → 앱으로 이어지는 실시간 데이터 연동

기간 · 인원

  • 2026.03 ~ 2026.08
  • 이다연 (APP·EM) · 염세현 (BE·EM) · 이지우 (AI)

맡은 역할

ESP32 STA 펌웨어 개발 (C · ESP-IDF)
  • Wi-Fi STA 모드로 공유기에 접속해 ESP32에서 CSI(64개 서브캐리어)를 실시간 수집
  • 수집한 CSI 원신호를 UDP로 서버에 전송, 자동 재연결로 끊김 없이 스트리밍 · Doxygen 주석으로 함수 단위 문서화
Android 앱 개발
  • 실시간 낙상 감지 결과·보호자 알림 화면, 기기 등록·선택·상태 확인 화면 구현
  • 서버(MQTT)로 수신한 위험 상태를 앱 UI에 실시간 반영

주요 성과

  • 약 50개 팀 참가 → 예선 30팀 → 본선 15팀 통과
  • 최종 장려상 수상 (은상과 1팀 차) · 현업 개발자·성인 참가자가 많은 대회
  • 가장 걱정했던 펌웨어–서버–앱 전체 연동을 완성해 실시연까지 진행
  • 프로젝트가 언론(전자신문)에 소개됨

문제 해결

앱–펌웨어 연동이 반복적으로 끊기는 문제

문제 배경

개발 중 휴대폰 핫스팟 환경에서 앱과 펌웨어를 연동해 테스트했는데, 통신이 주기적으로 끊겨 데이터 수신이 불안정했습니다.

해결 방법

원인이 핫스팟이 UDP 트래픽을 주기적으로 차단하는 데 있음을 확인하고 별도 공유기 환경으로 전환해 안정적인 통신을 확보했습니다.

통신 기능을 STA 모드에 둘지 AP 모드에 둘지

문제 배경

앱 연결과 서버 전송 기능을 STA 모드에서 처리할지 AP 모드에서 처리할지 결정해야 했고, 두 방식은 연결 안정성·초기 설정·서버 접근성에서 장단점이 달랐습니다.

해결 방법

서버 전송과 안정적인 연결이 핵심 요구사항이라 판단해 기존 네트워크에 접속하는 STA 모드로 통신 구조를 구성했습니다. 기술보다 요구사항을 먼저 정의하고 방식을 고른 과정이었습니다.

회고

ESP32 펌웨어를 직접 구조부터 작성하며 CSI 원신호를 끊김 없이 수집·전송하는 통신 로직을 다뤘고, 통신을 STA/AP 중 어디에 둘지 고민하며 '기술을 먼저 정하기보다 요구사항을 먼저 정의해야 한다'는 것을 배웠습니다. 헤더/소스 분리와 함수 단위 주석으로 협업자가 읽을 수 있는 펌웨어를 처음 의식했고, 가장 걱정했던 펌웨어–서버–앱 전체 연동을 완성해 실제 서비스처럼 동작시킨 경험이었습니다.

개요

차량 지붕에 카메라와 Jetson을 달고 주행하면 지나치는 배전 전주 상단의 위험 요소(까치집·수목)를 자동으로 촬영·판정해 서버·대시보드에 기록하는 시스템입니다. 원본 영상은 기기 밖으로 내보내지 않고 판정 결과와 사진만 전송해 프라이버시를 지킵니다. 저는 카메라 입력부터 서버 연동까지의 Edge Vision 파이프라인을 담당했습니다.

주요 성과 (실보드 측정)

  • 엣지 파이프라인 처리량 15fps → 30fps(2배), E2E 지연 66ms → 20ms(약 70%↓)
  • 30분 연속 실연동 구동에서 FPS 29.97 고정·크래시 0·예외 60건 전부 격리 (드롭 0.43%)

기간 · 인원

  • 2026.09 ~ 2026.10
  • 이다연 (Edge Vision·서버) · 염세현 (스트리밍·AI)

맡은 역할

카메라 입력 · 프레임 처리 (V4L2 · OpenCV)
  • V4L2로 USB 카메라 MJPG 1280×720 30fps 확보, 고정노출(≈1/1000s)로 주행 중 모션블러 억제
  • camera.py: 캡처 전용 스레드 + 바운드 큐(생산자–소비자) 구조로 추론 부하가 캡처를 막지 않게 설계, 프레임 드롭 카운터로 드롭 0% 측정
  • best_frame.py: Laplacian variance로 전주당 가장 선명한 한 장을 선택
엣지 통합 · 서버 연동
  • metrics.py(온도·전력·fps 실측) · gps.py(u-blox NMEA 파싱) · pipeline.py(카메라+지표+GPS+전송 오케스트레이션) 구현
  • telemetry_client.py: WebSocket 실시간 전송 + 자동 재연결·오프라인 버퍼로 유실 없는 전송
  • FastAPI + SQLite 서버 구축, 프론트 계약에 맞춰 전 엔드포인트 e2e 검증 및 계약 회귀 테스트 작성

문제 해결

성능이 안 나오는데, 추론이 아니라 카메라가 병목이었다

문제 배경

30fps가 목표였지만 15fps에 머물렀습니다. 처음엔 AI 추론을 의심했지만, 성능 측정 도구로 단계별 지연을 쪼개 보니 E2E 66ms 중 카메라 캡처가 45ms(68%)였고 추론은 13ms·GPU 28%뿐이었습니다.

해결 방법

병목이 MJPG를 CPU로 디코딩하는 데 있음을 데이터로 확인하고 이를 NVDEC 하드웨어 디코드로 옮긴 뒤 캡처를 스레드로 분리했습니다. 그 결과 15fps → 30fps, E2E 66ms → 20ms를 달성했습니다. '감'이 아니라 측정으로 방향을 잡은 것이 핵심이었습니다.

주행 중 Wi-Fi가 끊기면 데이터가 유실되는 문제

문제 배경

이동하며 촬영하다 보니 네트워크가 자주 끊겼고, 그때마다 전송 중이던 판정 결과·기기 상태가 유실될 수 있었습니다.

해결 방법

자동 재연결과 오프라인 버퍼를 두어 연결이 끊겨도 데이터를 순서대로 보관했다가 복구되면 유실 없이 전송하도록 구현했습니다.

안정성 · 장애 복구 (실하드웨어 검증)

  • 실카메라→실탐지→실서버 30분 연속 + 30초마다 예외 주입: FPS avg 29.97 · E2E p95 22ms, 드롭 0.43%, 예외 60건 전부 격리 · 크래시 0
  • 카메라 USB 단절 자동 재오픈: 실제 USB unbind/rebind로 검증 (단절 중 버티다 재연결 시 자동 복구)
  • 프레임 단위 예외 격리 + 오프라인 버퍼 상한으로 session·detection 무손실 보존

산출물 · 확장 여지

  • 엣지 모듈: camera.py · best_frame.py · metrics.py · gps.py · telemetry_client.py · pipeline.py
  • 서버: FastAPI · SQLite · 계약 회귀 테스트
  • 추론 여유(GPU 33%)로 2단 추론(검출→분류)까지 확장 가능

회고

팀원이 만든 AI 탐지 결과를 실제 하드웨어 위에서 하나의 시스템으로 이어 붙이는 Edge Vision 파이프라인을 맡으며 성능을 '감'이 아니라 프레임 드롭·지연·온도·전력 같은 실측 지표로 검증하는 것의 중요성을 배웠습니다. 엣지 파이프라인을 실보드에서 검증하고, 팀원의 탐지 모델 연동까지 구동을 확인했습니다.

문제 배경

좌우 회피 동작이 불균형한 문제

문제 배경

해결 방법

회고
