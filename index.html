개요

카메라 없이 Wi-Fi 신호의 미세한 변화(CSI)를 분석해 실내 낙상을 감지하는 시스템입니다. 사생활 침해 없이 고령자의 낙상을 감지하는 것을 목표로, ESP32로 수집한 신호를 딥러닝 모델로 판별하고 결과를 Android 앱으로 전달해 보호자가 즉시 확인할 수 있도록 구현했습니다.

기간 · 인원

  • 2026.03 ~ 2026.08
  • 이다연 (APP·EM) · 염세현 (BE·EM) · 이지우 (AI)

주요 기능

  • 카메라 없이 Wi-Fi CSI로 실내 낙상을 실시간 감지
  • 낙상 감지 시 보호자 앱으로 즉시 알림 전송
  • 기기 등록·선택 및 상태 확인
  • ESP32 → 서버 → 앱으로 이어지는 실시간 데이터 연동

맡은 역할

ESP32 STA 펌웨어 개발
  • Wi-Fi STA 모드로 공유기에 접속해 ESP32에서 CSI(Channel State Information) 신호를 실시간 수집
  • 수집한 CSI 원신호(64개 서브캐리어)를 서버로 전송하는 통신 로직 구현
  • 연결 유지·재연결 처리로 신호가 끊기지 않도록 전송 흐름을 안정화
  • 헤더(.h)/소스(.c) 분리, @brief·@param 등 Doxygen 스타일 주석으로 함수 문서화
  • 함수·변수 역할과 코드 구조를 정리하며 펌웨어 기본기 확립
Android 앱 개발
  • 실시간 낙상 감지 결과 표시 및 보호자 알림 화면 구현
  • 기기 등록·선택·상태 확인 화면 구현
  • 서버(MQTT)로 수신한 위험 상태를 앱 UI에 실시간 반영

주요 성과

  • 약 50개 팀 참가 → 예선 30 → 15팀 통과, 본선 진출
  • 최종 장려상 수상 (은상과 1팀 차)
  • 펌웨어–서버–앱 전체 연동을 완성해 실시연까지 진행

문제 해결

앱–펌웨어 연동이 반복적으로 끊기는 문제

문제 배경

개발 중 휴대폰 핫스팟 환경에서 앱과 펌웨어를 연동해 테스트했는데, 통신이 주기적으로 끊겨 데이터 수신이 불안정했습니다.

해결 방법

원인이 핫스팟이 UDP 트래픽을 주기적으로 차단하는 데 있음을 확인하고, 별도 공유기 환경으로 전환해 안정적인 통신을 확보했습니다.

통신 기능을 STA 모드에 둘지 AP 모드에 둘지

문제 배경

앱 연결과 서버 전송 기능을 ESP32의 STA(기존 Wi-Fi 접속) 모드에서 처리할지, AP(기기가 직접 네트워크를 제공) 모드에서 처리할지 결정해야 했습니다. 두 방식은 연결 안정성, 초기 설정 편의성, 서버 접근성에서 장단점이 달랐습니다.

해결 방법

서버로의 데이터 전송과 안정적인 연결이 핵심 요구사항이라고 판단해, 기존 네트워크에 접속하는 STA 모드를 기준으로 통신 구조를 구성했습니다. 기술을 먼저 정하기보다 요구사항을 먼저 정의하고 모드를 선택하는 과정이었습니다.

회고

가장 걱정했던 펌웨어–서버–앱 전체 연동이 예상보다 잘 풀려 실제 서비스처럼 동작하는 것을 확인했을 때 큰 성취감을 느꼈습니다. 펌웨어를 직접 구조부터 작성하며 처음으로 코드를 짜는 재미와 자신감을 얻었고, 통신 구조를 어디에 둘지 고민하며 '기술을 먼저 정하기보다 요구사항을 먼저 정의해야 한다'는 것을 배웠습니다. 예선에서는 확장성 관련 Q&A에 잘 답하지 못했지만 본선에서는 발표 연습을 거듭해 안정적으로 마쳤고, 현업 개발자·성인 참가자가 많은 대회에서 장려상을 받으며 결과보다 과정에서 더 많은 것을 얻은 프로젝트였습니다.

개요

차량 지붕에 카메라와 Jetson을 달고 주행하면, 지나치는 배전 전주 상단의 위험 요소(까치집·수목)를 자동으로 촬영·판정해 서버·대시보드에 기록하는 시스템입니다. 원본 영상은 기기 밖으로 내보내지 않고 판정 결과와 사진만 전송해 프라이버시를 지킵니다. 저는 카메라 입력부터 서버 연동까지의 Edge Vision 파이프라인을 담당했습니다.

기간 · 인원

  • 2026.09 ~ 진행중
  • 이다연 (Edge Vision·서버) · 염세현 (스트리밍·AI)

주요 기능

  • 주행 중 전주 상단을 자동 촬영하고 위험(까치집·수목)을 판정
  • 원본 영상은 기기 밖으로 전송하지 않고 판정 결과·사진만 서버로 전송 (프라이버시)
  • 온도·전력·GPS 등 기기 상태를 실측해 함께 전송
  • 네트워크가 끊겨도 유실 없이 순서를 보존해 실시간 전송

맡은 역할

카메라 입력 · 프레임 처리 (V4L2 · OpenCV)
  • V4L2로 USB 카메라 MJPG 1280×720 30fps 확보, 고정노출(≈1/1000s)로 주행 중 모션블러 억제
  • camera.py — 캡처 전용 스레드 + 바운드 큐(생산자–소비자) 구조로 추론 부하가 캡처를 막지 않게 설계, 프레임 드롭 카운터로 드롭 0% 측정
  • best_frame.py — Laplacian variance로 전주당 가장 선명한 한 장을 선택
엣지 통합 · 서버 연동
  • metrics.py(온도·전력·fps 실측) · gps.py(u-blox NMEA 파싱) · pipeline.py(카메라+지표+GPS+전송 오케스트레이션) 구현
  • telemetry_client.py — WebSocket 실시간 전송 + 자동 재연결·오프라인 버퍼로 유실 없는 전송
  • FastAPI + SQLite 서버 구축, 프론트 계약에 맞춰 전 엔드포인트 e2e 검증 및 계약 회귀 테스트 작성
Jetson 엣지 환경
  • Jetson Orin Nano 세팅(JetPack·CUDA·TensorRT), 더미 YOLO(ONNX → TensorRT FP16)로 추론 배관을 사전 검증

문제 해결

추론 부하가 카메라 캡처를 막아 프레임이 밀리는 문제

문제 배경

AI 추론과 카메라 캡처가 한 흐름에 묶이면, 추론이 느려질 때 프레임이 밀려 드롭이 발생하고 주행 영상이 끊깁니다.

해결 방법

캡처 전용 스레드와 바운드 큐(생산자–소비자)로 캡처와 처리를 분리해, 추론 부하와 무관하게 캡처가 유지되도록 설계했습니다. 프레임 드롭 카운터로 '드롭 0%'를 수치로 검증했습니다.

주행 중 Wi-Fi가 끊기면 데이터가 유실되는 문제

문제 배경

이동하며 촬영하다 보니 네트워크가 자주 끊겼고, 그때마다 전송 중이던 판정 결과·기기 상태가 유실될 수 있었습니다.

해결 방법

자동 재연결과 오프라인 버퍼를 두어, 연결이 끊겨도 데이터를 순서대로 보관했다가 복구되면 유실 없이 전송하도록 구현했습니다.

회고

팀원이 만든 AI 탐지 결과를 실제 하드웨어 위에서 하나의 시스템으로 이어 붙이는 Edge Vision 파이프라인을 맡으며, 성능을 '감'이 아니라 프레임 드롭·온도·전력 같은 실측 지표로 검증하는 것의 중요성을 배우고 있습니다. (Vision 추론 연동은 진행 중)

개요

자율주행 로봇이 축사를 순찰하며 가스·온습도·미세먼지·열화상·배설물을 실시간으로 감지하고, 위험을 판단해 알림·인터록까지 수행하는 모니터링 시스템입니다. 저는 ROS2 노드 구조 전체를 직접 설계하고 인지·분석 노드를 구현했습니다.

기간 · 인원

  • 2026.06 ~ 2026.10
  • 이다연 (ROS·AI) · 손서원 (FPGA) · 염세현 (BSP)

주요 기능

  • 가스·온습도·미세먼지·열화상 실시간 수집 및 대시보드 시각화
  • 카메라 + 열화상 기반 배설물 위치 탐지
  • 가스 농도 예측·위험 등급 산출 → 임계 초과 시 알림 및 인터록 명령
  • 위험 구역을 회피하며 Nav2로 자율 순찰

맡은 역할

ROS2 노드 아키텍처 설계
  • 센서 수집(sensor_bridge) → 인지·분석 → 위험 판단(risk_assessor) → 순찰·알림·인터록으로 이어지는 노드 구조를 역할 단위로 직접 설계
  • 센서 raw → 분석 → 위험 등급 → 인터록 명령까지의 토픽 파이프라인과 barn_msgs 커스텀 메시지 정의
  • Nav2 액션(navigate_to_pose) 연동으로 위험 구역 회피 순찰 노드 구성
인지·분석 노드 구현
  • 카메라·열화상 기반 배설물 탐지 노드 구현 (Python)
  • 가스 농도 평가·예측 및 위험 등급 이벤트 분할 노드 구현

문제 해결

기능을 한 노드에 몰면 병목·강결합이 생기는 문제

문제 배경

센서 수집·인지·분석·위험 판단·순찰·알림이 서로 얽혀 있어, 한 노드에 몰아넣으면 병목이 생기고 유지보수·확장·디버깅이 어려워지는 구조였습니다.

해결 방법

기능을 노드 단위로 분리하고 토픽으로 느슨하게 연결했습니다. 센서 → 분석 → 위험 판단 → 인터록으로 이어지는 단방향 파이프라인과 커스텀 메시지(barn_msgs)를 먼저 정의해, 노드를 독립적으로 개발·교체·디버깅할 수 있는 구조로 만들었습니다.

회고
